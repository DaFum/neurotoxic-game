# api/leaderboard - Agent Instructions

- Resolve submitted song IDs through the canonical song/leaderboard mapping (`SONGS_BY_ID.get(songId).leaderboardId`); never persist raw UI song IDs.
- Do not expose internal storage keys through public response shapes.
- Keep failure response shapes deterministic — security and node suites assert exact error bodies.
- `playerId` is a client-generated localStorage UUID and the ONLY authorization a write carries — the write endpoints have no auth. It must never appear in a GET response: publishing it lets any reader rename that player and overwrite their scores. Responses expose `toPublicPlayerRef(playerId)` (`lib/apiUtils.js`) instead, a one-way hash that is stable enough to use as a client list key. `src/ui/bandhq/leaderboard` consumes it as `playerRef`.
- The client already resolves song IDs before submitting (`src/utils/leaderboardUtils.ts` sends `SONGS_BY_ID.get(id).leaderboardId`), so the server allowlist in `lib/leaderboardSongIds.js` holds leaderboard IDs, not UI IDs. All 7 UI IDs differ from their leaderboard ID (`01 Kranker Schrank` → `01_kranker_schrank`), so rejecting a raw UI ID is intended, not a bug. `tests/api/leaderboard.song.test.js` pins the allowlist against `SONGS_BY_ID` so the two cannot drift.
- `stats.js` accepts an optional monotonic `revision` per player. With one, a single Lua script writes the revision, the display name and all boards atomically (never write the name outside it: an older request finishing late would pair new scores with an old name) and drops a request whose revision is not newer (`{ success: true, stale: true, revision }`, the stored revision, so the client can catch up); without one it writes (last-write-wins) only while the player has no stored revision. Once `lb:revision` holds an entry for the player, an unversioned request is refused with the same stale acknowledgement and writes nothing (`WRITE_IF_UNVERSIONED_SCRIPT`, atomic like the versioned one, never creating a revision itself), so an old cached bundle cannot roll a revision-protected player back; it simply stops updating that player's boards. `song.js` writes the name through `SET_NAME_IF_UNVERSIONED_SCRIPT` (one script, same `HEXISTS lb:revision` boundary): a player with a stored revision keeps the name its stats snapshot wrote, a song-only player is still named; a refused name never changes the response or the `GT` score writes. The client (`useLeaderboardSync`) persists the revision before sending and never reuses or lowers it. Rankings stay honor-based: nothing verifies the values (see `docs/audits/2026-10-22-r03-proxy-rate-limit-audit.md`).
- Revision ceiling (#3475): `stats.js` rejects `MAX_SAFE_INTEGER`, so a player whose `lb:revision` entry is `MAX_SAFE_INTEGER - 1` or higher can never be overtaken. The client (`src/utils/leaderboardSyncController.ts`) then stops syncing that player for the session and never persists a ceiling revision, so the next session's first request probes again with a clock-derived revision. There is deliberately no reset endpoint: with no auth, a reset trusting `playerId` authorizes nothing, and accepting a lower revision breaks monotonicity. Until real auth exists an operator resets an affected player by hand with `HSET lb:revision <playerId> <current epoch ms>`. Never `HDEL` the entry (that reopens last-write-wins writes from old unversioned bundles), and never set a value below the current time (a request allocated before the reset must still be dropped). The client treats a stored revision at or above `MAX_SAFE_INTEGER - 1` as unusable (#3494) and derives the next one from the clock, so a browser that persisted the ceiling recovers after the reset without clearing its storage.
- `song.js` uses the `GT` flag so a submission can only raise a player's best. `stats.js` deliberately does NOT: those boards track CURRENT stats and money legitimately decreases, so `GT` would silently redefine `lb:balance` as "peak balance ever".
- `stats.js` publishes money above `MAX_PUBLISHED_BALANCE` (`lib/leaderboardLimits.js`, shared with the client) at the cap instead of rejecting the payload, so one rich balance cannot stop fame, followers and the other stats from syncing. Non-finite or negative money is still a 400.
