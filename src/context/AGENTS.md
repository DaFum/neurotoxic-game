# src/context - Agent Instructions

## Actions & Toasts

- Action creators return `Extract<GameAction, { type: typeof ActionTypes.X }>`; do not hand-write the action object shape, or the union stops narrowing in the reducer.
- `useGameActions()` exposes named action methods, not raw reducer dispatch. New context-level actions must be added to `GameDispatchActions`, implemented in `GameStateProvider`, included in `dispatchValue`, and covered by tests.
- Toast `options` values must be primitive-only: `string | number | boolean | null`. Sanitizers drop non-primitive and forbidden-key entries; do not preserve them by stringifying.
- `UPDATE_SOCIAL` accepts both `Partial<SocialState>` and a functional updater `(prev) => Partial<SocialState>`. `socialReducer` evaluates the function against current state at reducer time; do not pre-compute against `stateRef` in the caller.
- `UPDATE_SOCIAL` has one whitelist, `sanitizeSocialUpdates` (`stateSanitizers.ts`), run by both `createUpdateSocialAction` and `handleUpdateSocial`: unknown and hostile keys (`__proto__`, `constructor`, `prototype`) are dropped, non-finite values on the numeric `SocialState` fields are dropped (`null` survives only on the nullable `last*` fields), and follower counts, `reputationCooldown` and the `last*Day` markers are floored at 0. The creator wraps the functional updater so sanitization also runs after it resolves. Reducer-side checks (`trend`, `activeDeals`, range clamps) remain final authority — do not remove them.
- `createUpdateSettingsAction` delegates to `sanitizeSettingsPayload` (the canonical sanitizer in `src/utils/settingsSanitizer.ts`, shared by the reducer's `LOAD_GAME`/`UPDATE_SETTINGS` handling and the global-storage write), which owns the key whitelist (`crtEnabled`, `tutorialSeen`, `logLevel`) and the per-value validation. Adding a new settings field means extending `sanitizeSettingsPayload` only.
- `updateSettings` must run `sanitizeSettingsPayload(updates)` before `writeGlobalSettings`; never spread raw `updates` into global storage, or malformed/unknown keys (e.g. a non-numeric `logLevel`) bypass the reducer's validation and persist globally.
- `gig_intro` / `gig_mid` events are exempt from `useEventSystem`'s GIG-scene block and daily `eventsTriggeredToday` cap; do not re-block them. See `triggerEvent` in `src/utils/AGENTS.md`.

## Persistence

- Autosave is centralized in `usePersistence`'s `shouldAutosaveOnTransition` effect (fires on `GIG → POST_GIG` and `POST_GIG → (GAMEOVER | OVERWORLD)`). Do not add explicit `saveGame()` calls to handlers that perform those same transitions; intentional travel/arrival/Overworld manual saves are separate.
- Use `saveGameAfterStateCommit()` when a scene-changing transition will unmount the calling hook before it can observe committed state. The provider-level persistence effect owns that flush.
- Save key is `SAVE_KEY = 'neurotoxic_v3_save'`; `PERSISTED_FIELDS` in `usePersistence.ts` is the single source of truth for persisted save fields. Both the load whitelist (`LOADABLE_SAVE_KEYS`) and the `createPersistedState` snapshot are derived from it. New persisted fields require this checklist:
  1. Add one `<key>: <predicate>` entry to `PERSISTED_FIELDS`.
  2. Sanitize/read it in the reducer's `LOAD_GAME` handler (`handleLoadGame` in `systemReducer.ts`).
     Fields needing special save-time handling (`timestamp`, `unlocks`, `setlist`) are written explicitly in `createPersistedState`.
- Save slots are version-specific: `getSaveSlotKey(version)` is `SAVE_KEY` up to version 2 (every shipped build; no migration) and `SAVE_KEY.v<N>` from version 3 on. `saveGame` writes only `getSaveSlotKey(CURRENT_SAVE_VERSION)`; `loadGame` reads the highest slot it supports, else `SAVE_KEY`, and never deletes a lower slot (it doubles as rollback); `deleteSave` removes `SAVE_KEY` and every `.v<N>` slot, or loading would resurrect deleted progress; "a save exists" checks go through `hasStoredSave`. Any slot above `CURRENT_SAVE_VERSION`, or a newer payload in `SAVE_KEY`, makes `saveGame` AND `loadGame` refuse (incompatible-version message), so a rolled-back build never holds a session it cannot save; an unreadable slot also refuses saves (notice once per session) and loads (`reason: 'unreadable'`, its own message, never "No save found"). Scope: the cross-tab check-then-write race is closed only between builds that write their own slot (v3+); builds sharing `SAVE_KEY` (all shipped builds) cannot be fixed retroactively, and an old tab that was already running and keeps writing `SAVE_KEY` after a v3 slot appears diverges silently, the v3 slot winning on the newer build's next load.
- Adding a **required** top-level `GameState` field (not just persisted) also needs a default in `initialState` (and a fresh reset in `createInitialState` for arrays/objects, to avoid shared-reference mutation) and an entry in the playwright screenshot `BASE_STATE` (`.claude/skills/playwright-screenshot/scripts/screenshot-state-inject.js`). `tests/node/playwright-screenshot-fixture-validation.test.js` asserts `BASE_STATE` mirrors every `initialState` field and fails CI otherwise.
- `terminalOutcome` is the durable record that the Career ended (`event_game_over`, `bankruptcy`, `career_victory`, `stranded`). Every way into GAMEOVER must leave one: settlement reducers and `SET_TERMINAL_OUTCOME` set it explicitly, and `handleChangeScene` derives it for the live Continue/stranded paths that only change scene. `handleLoadGame` routes any save carrying it to GAMEOVER and settles a run it left active (a victory settles none: a real one is only recorded with no run active, so a stale `tourCompleted` flag is not read as one while a run is live, and a victory claimed over a live run is dropped on load). A save written at GAMEOVER before endings were recorded gets its ending derived on load, so a save written at GAMEOVER never reloads as OVERWORLD; its defeat is always `bankruptcy`, never `stranded` (the stranded check then saved at OVERWORLD, before its scene change). A load with no ending clears a stale `tourCompleted`. The stranded check saves before its scene change, so `usePersistence` also autosaves the OVERWORLD → GAMEOVER transition; that save is the one that carries the ending. `SET_TERMINAL_OUTCOME` and `CHANGE_SCENE` into GAMEOVER both settle an active run as failed through one mapping (`stranded` → `fuel_stranded`, `bankruptcy`, `event_game_over`); the cause that ended the Career wins over a crisis the run had pending, and a victory settles none. `RESET_STATE` clears it.
- `pendingSupplyStopInventory` is persisted but transient: `handleLoadGame` always takes it from the save (null when absent) through `sanitizeShopInventoryItem`, capped at 24 items, so a load over a live session closes that session's shop.
- `neurotoxic_inject_marker` localStorage flag is a screenshot/E2E-only hydration channel; the marker is removed in a `useEffect` after mount (not in `initGameState`) to survive StrictMode's double-invoked lazy initializer.
- `normalizeLoadedGameMap` coerces stringy node `x`/`y` back to numbers for legacy saves. When adding persisted `GameMap` or map-node fields that old saves may contain, extend this normalizer rather than the reducer's load path.

## Long-Term Assets

- Asset action creators (`assetActionCreators.ts`) normalize payloads via `finiteNumberOr` and strip prototype keys before validation. DIY+loan returns `PURCHASE_CHASSIS_FAILED` (typed) — never `null`.
- `purchaseChassis` enforces loan-profile eligibility against `state.player.fame` (NOT `state.band.fame`) and `state.social.scenePresence`; ineligible profiles return `PURCHASE_CHASSIS_FAILED` with reason `LOAN_PROFILE_INELIGIBLE`. Add new gating fields to the same union when extending `LoanProfile`.
- `purchaseChassis` rejects `mode: 'crowdfund'` (`CROWDFUND_REQUIRES_CAMPAIGN`) and `handlePurchaseChassis` only accepts `cash`/`loan` payloads — crowdfund acquisition exists solely via `startCrowdfund` + `processCrowdfundTick`. Without both guards a crowdfund-mode dispatch would mint a free chassis (neither payment branch fires).
- `startCrowdfund` derives `plannedSuccessProbability` (`resolveCrowdfundProbability` from the player's fame and scene presence plus the target) and `plannedSuccessRoll` (`mulberry32(rngSeed ^ fameStake ^ days)`) from state and caps `fameStake` at the player's fame; callers pass none of them. The setup modal previews the same formula, so the tick resolves `roll < probability` against the displayed odds.
- `INSTALL_MODULE` allows flavor-mix between module and chassis (legit module on DIY chassis is intentional).
